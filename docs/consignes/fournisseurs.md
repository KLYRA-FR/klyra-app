# Fournisseurs, consommation et contexte

- **Consommation** : `electron/consommation.ts` tient un journal (`consommation.jsonl` dans le dossier de l’app) des jetons et coûts renvoyés par Claude Code (écart du `modelUsage` cumulé, à chaque `result`) et par les autres IA (`usage`). Jamais de contenu de message. Le Profil en tire ses chiffres (`src/lib/consommation.ts`) ; NEVER de chiffre estimé ou inventé : sans donnée, un état vide. `electron/historique.ts` rattrape toute la consommation Claude Code du poste dans ses transcriptions (`$CLAUDE_CONFIG_DIR` ou `~/.claude/projects`) : sessions de l’app (marquées `klyra`, seulement avant le journal) et des autres outils ; incrémental. `electron/anthropic-admin.ts` : usage et coût réels d’une organisation Console, facultatif (clé Admin chiffrée). Test : `pnpm build:electron && pnpm test:consommation` (aussi en CI Windows).
- **Utilisation des abonnements** (anneaux du rail, `UtilisationRail` dans `src/components/chat/CarteUtilisation.tsx`) : un anneau par fournisseur connecté du serveur affiché (`useMoteurs(useLieuActif())`), Claude et ChatGPT par son compte ; lecture par `electron/utilisation.ts` (module pur, généré en `serveur/utilisation.mjs`), méthodes `utilisation` / `surUtilisation` des moteurs, IPC `moteurs:utilisation` aiguillé par le `lieu`, route `moteurs/<id>/utilisation` du VPS. NEVER de chiffre estimé : une fenêtre non donnée reste vide. Relire Claude Code sur ce PC coûte une petite requête (au clic seulement) ; Codex et le VPS se relisent gratuitement. Nouveau moteur à abonnement → son lecteur dans `utilisation.ts` et son logo dans `FOURNISSEURS`. Tests : `pnpm test:moteurs`, `pnpm test:serveur-fournisseurs`.
- **Grok** (moteur `grok`, Grok Build de xAI) : `grok agent stdio`, l'Agent Client Protocol, par un seul client pour le PC et le VPS (`electron/moteurs/acp.ts`, généré en `serveur/acp.mjs` ; PC : `electron/moteurs/grok.ts`, VPS : `serveur/grok.mjs`). Les consignes de la session vont dans `_meta.rules`, l'accès complet dans `_meta.yoloMode`, les autres accès dans `session/set_mode`. Le modèle et l'effort passent par `session/set_config_option` (`{ value }`). Un outil MCP arrive en `serveur__outil` et devient `mcp__serveur__outil`. `ENV_GROK` coupe ce que Grok lirait de Claude Code (skills, MCP) et sa mise à jour automatique. Les skills allumées sont présentées comme pour Codex (`consigneSkillsCodex`). Grok n'appelle pas les agents de l'app (ses sous-agents viennent de `~/.grok/agents`). Connexion : `grok login` sur le PC, `grok login --device-auth` sur le VPS (`lireCodeAppareil`) ; clé de console.x.ai en repli, chiffrée sur le PC (`grok-cle.json`), en 600 sur le VPS (`donnees/grok.json`), donnée au processus seulement (`XAI_API_KEY`). Documentation : celle qui est embarquée dans le binaire (pages `15-agent-mode.md`, `22-permissions-and-safety.md`…). Tests : `pnpm test:moteurs` (faux Grok, `scripts/faux-acp.mjs`), `pnpm test:serveur-grok`, `xvfb-run -a pnpm test:moteur-grok -- --no-sandbox` (après `build:electron`). Avec `KLYRA_GROK_PATH`, les deux derniers tournent sur le vrai Grok Build.
- **Configuration KLYRA** (`electron/configuration-klyra.ts`, module pur lu par le process principal et l'écran ; `reglages.configuration`) : ce que l'app propose pour que les agents consomment moins, adopté en un clic (carte de l'Accueil `CarteConfiguration`, Réglages › Agents `GroupeConfigurationKlyra`), jamais appliqué d'office, modifiable, réversible, et seulement pour les sessions de l'app. **Consignes KLYRA** : un texte ajouté par `consignesApp` (donc Claude Code et Codex), modifiable ; le modèle a une version (`MODELE_CONSIGNES`), un texte resté tel quel suit la nouvelle (`MODELES_PRECEDENTS`), un texte modifié la voit proposée. **Mémoire des agents** coupée : `CLAUDE_CODE_DISABLE_AUTO_MEMORY` dans `environnementAgent` (~4 000 jetons par appel d'un agent qui a `memory`), sans toucher aux fiches. Changer l'un ou l'autre change la signature des sessions (`signatureConfiguration`). Le VPS reçoit la configuration avec l'équipe (`equipePourVps`, dans l'empreinte) et l'applique à toutes ses sessions (PC, téléphone, routines), Codex compris pour les consignes. **Diagnostic du poste** (`electron/diagnostic-poste.ts`, Réglages › Agents) : ce que la configuration personnelle de Claude Code ajoute à chaque appel (CLAUDE.md personnel et ses imports, skills personnelles, présentation des agents actifs, plugins, serveurs MCP), estimé à 2,75 caractères par jeton, avec un conseil et « Montrer » (seulement un chemin que le diagnostic vient de trouver). Les skills personnelles se coupent par agent (Réglages › Agents, `skillsParAgent`) sans retirer les agents ni les CLAUDE.md. `--setting-sources project,local` retire aussi le dossier préparé (agents, skills, CLAUDE.md) : on ne le combine pas avec `CLAUDE_CONFIG_DIR`. `CLAUDE_CODE_DISABLE_CLAUDE_MDS` retire aussi les AGENTS.md des projets. Sur un VPS : Réglages du serveur › Général (« Ce que ce serveur ajoute », route `agent/diagnostic`, module généré `serveur/diagnostic-poste.mjs`), sans « Montrer ». Tests : `pnpm test:configuration` (Electron, vrai Claude Code, faux fournisseur), `src/lib/configuration-klyra.test.ts`, `pnpm test:diagnostic-poste`.
- **Consignes d'un projet** (`electron/consignes-projet.ts`, `ConsignesProjet` sur l'écran d'un projet de ce poste) : « Ajouter les consignes KLYRA » montre d'abord ce qui sera écrit, puis crée un AGENTS.md court à remplir (but, commandes de vérification devinées d'après le package.json et le verrou, où sont les choses, règles) et un CLAUDE.md d'une ligne `@AGENTS.md`. Claude Code le lit alors à toutes les versions, une seule fois (+59 jetons, vérifié), et Codex lit l'AGENTS.md. Jamais d'écrasement : une création échoue si le fichier est apparu (`wx`), un CLAUDE.md existant reçoit seulement l'import en tête, une fois. IPC `projets:consignes` et `…:ecrire`, aiguillés par le `lieu` du projet : sur un VPS, routes `fichiers/consignes` (GET l'état, POST l'écriture) et module généré `serveur/consignes-projet.mjs` ; « Ouvrir AGENTS.md » l'ouvre dans la visionneuse. Tests : `pnpm test:consignes-projet` (module, puis Electron).
- **Taille des conversations** (`src/lib/contexte.ts`, `ConseilContexte`) : chaque appel principal envoie `contexte` (ce qu'il a relu : entrée + cache lu + cache écrit), gardé par agent dans `chat.contexte` avec le socle de la session (premier appel) et la session mesurée ; `/compact` part tel quel (`construirePrompt`), sa réponse est marquée `compaction` (pas une réponse pour `aReprendre`) et `compact_boundary` la termine (résultat vide), en local comme sur le VPS (`serveur/agents.mjs`). Le conseil au-dessus du composeur porte sur les échanges (taille moins socle) : lourde (≥ 50 k) → « Résumer la conversation » ; reprise après plus d'une heure (cache expiré, ≥ 30 k) → « Nouveau fil » là où il y a des fils (un résumé ne rattraperait pas la relecture) ; « Plus tard » jusqu'à +20 k. **Résumé automatique** (configuration KLYRA `resumeAuto`, désactivé par défaut et hors de la configuration recommandée tant qu'il n'est pas mesuré) : l'app envoie elle-même `COMMANDE_RESUME_AUTO` (`/compact` et ce qu'il faut garder) par `compacterAuto` ; la commande reste hors du fil, la réponse porte `compactionAuto` (`envoi` ou `pause`) et une note. Avant un message à un agent dont les échanges dépassent 80 k (`resumeAvantEnvoi`) : le message attend dans la file, le résumé passe d'abord. Pendant une pause de 25 à 55 min avec au moins 40 k d'échanges (`resumePause`) : une tentative par mesure, un à la fois, vérifié 5 s après l'ouverture puis chaque minute. Jamais pendant qu'un agent travaille. Un résumé n'est pas une réponse : ni notification, ni son, ni ticket, ni retour de fil. Pas de `CLAUDE_CODE_AUTO_COMPACT_WINDOW` : Claude Code résume aussi en plein travail, et a un plancher (~75 k). Tests : `pnpm test:contexte`, `pnpm test:conseil-contexte` et `pnpm test:resume-auto` (après le build, profil temporaire).
