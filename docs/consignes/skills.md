# Skills

- **Skills (compétences)** : celles de l’app (`userData/bibliotheque-skills`, copiées une fois depuis `<config>/skills` ; sans ce dossier, celles du poste) et du projet (`.claude/skills`) ne partent chez un agent que si Réglages › Agents les laisse allumées pour lui (`electron/skills-par-agent.ts`, `skillOverrides` à `off` dans le `--settings` de sa session : les agents du poste et les CLAUDE.md restent). Une skill ajoutée ensuite dans `~/.claude/skills` n’est pas reprise. Réglages › Agents importe un dossier, ou reprend avec « Importer depuis le poste » les skills apparues ensuite dans `~/.claude/skills` (`importerSkills`) : sans écraser un nom déjà là, sans rien supprimer, et la skill importée reste éteinte tant qu’on ne l’allume pas. Le dossier préparé lie `plugins`, `settings.json` et `settings.local.json` du poste : les plugins activés (vercel, aircloud-tools) se chargent, rien n’est copié ni retiré. Le VPS reçoit, avec l’équipe, les dossiers des skills allumées pour au moins un agent et les écrit dans `donnees/bibliotheque-skills` : les sessions préparées et le filtre les lisent là (`KLYRA_USER_DATA` du serveur). Une skill éteinte pour tout le monde ne part pas. Rien n’est supprimé sur le poste ni dans `~/.claude` du VPS. Sans ce champ (ancien PC), la bibliothèque n’est pas touchée. Dès qu’elle existe, le VPS ne lit plus les skills de son `~/.claude`. Défaut : au premier lancement, les skills personnelles déjà présentes restent allumées pour les agents déjà là ; une skill personnelle nouvelle ou un agent nouveau ne les reçoit pas tant qu’on ne l’allume pas ; une skill de projet reste allumée tant qu’on ne la coupe pas. Rien n’est déplacé sur le poste. Au lancement, Claude Code lit un dossier préparé dans les données de l’app (`userData/preparation/<agent>`, `CLAUDE_CONFIG_DIR` seulement sur ce processus) : les fiches actives, seulement les skills personnelles allumées, un lien vers le CLAUDE.md personnel (ses imports `@./` restent valables), et des liens vers la connexion, les projets et les sessions du poste. On ne combine pas ce dossier avec `--setting-sources`. Un agent appelé reçoit les skills allumées pour lui : la copie de sa fiche retire l'outil Skill, qui montrerait le catalogue de celui qui l'a lancé. Codex a un processus par agent (`userData/preparation-codex/<agent>`, `CODEX_HOME` seulement sur ce processus) : seulement ses skills allumées (`filtreSkills`). Le processus du compte n'a pas ce dossier. La consigne (`consigneSkillsCodex`) reste pour le texte préchargé par la fiche. Un agent appelé reçoit les skills allumées pour lui, pas celles de celui qui l'a lancé. Prouvé le 04/11/2026 avec Claude Code 2.1.306 et Codex 0.164, faux fournisseurs. L’éditeur lit et écrit les fiches dans le dossier de l’app (`userData/equipe`) ; `~/.claude/agents` reste la copie d’origine, jamais supprimée. Celles livrées avec Claude Code restent coupées. Vérifié avec Claude Code 2.1.317 (`pnpm test:skills`, vrai Claude Code, faux fournisseur) : l’outil `Skill` charge sans demande d’autorisation à tout niveau d’accès ; `/<skill>` n’est reconnu qu’en tête du message, donc `promptAvecSkill` (`electron/connaissances-agent.ts`) remet la commande devant le contexte de l’app quand la skill existe (option `skill` de `StreamOptions`, posée par `workspace.tsx` d’après `src/lib/skills.ts`, Claude seulement) ; les `skills` d’une fiche sont préchargées par Claude Code pour un sous-agent mais pas pour un agent lancé seul (`--agent` : conversation directe, fils), donc `competencesPrechargees` les ajoute à ses consignes (et à la signature). Pareil sur le VPS, choix par agent compris (`serveur/connaissances-agent.mjs` et `serveur/skills-par-agent.mjs`, générés par `scripts/serveur-genere.mjs`, téléchargés par `lancer.sh`) ; le panneau Compétences et la liste « / » d’une conversation sur un VPS lisent les skills du serveur (`GET /klyra/v1/agent/competences`, mêmes gardes qu’un envoi ; `competencesVps`, l’équipe synchronisée d’abord), sans « Montrer » ; précharger une skill écrit la fiche de ce PC, copiée sur le VPS à la synchronisation suivante. Skills des plugins activés (`enabledPlugins`, `plugins/installed_plugins.json`, nom `<plugin>:<skill>`, vérifié par `claude plugin install`) : listées, préchargeables, demandables comme les autres (`lireSkillsPlugins`). Codex ne lit pas `.claude/skills` (seulement `.codex/skills` et `.agents/skills`, vérifié avec Codex 0.166) : `consigneSkillsCodex` les lui présente par leur fichier, avec le texte de celles que la fiche précharge, et `promptAvecSkillCodex` met la compétence demandée à lire en tête (PC et VPS ; `pnpm test:skills-codex`, vrai Codex, faux OpenAI). Le composeur propose les skills quand le message commence par « / » (avec Claude comme avec ChatGPT) ; le panneau Compétences ajoute ou retire une skill préchargée (`setListe`, liste YAML, par `save`). L’en-tête d’une fiche garde ses blocs YAML (`Frontmatter.blocs` : listes, sous-clés ; `>` et `|` dépliés) : NEVER de réécriture qui les perd. Tests : `pnpm test:skills`, `pnpm test:connaissances`, `src/lib/agent-file.test.ts`, `src/lib/skills.test.ts`.
