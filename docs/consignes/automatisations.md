# Routines, workflows et journal super-agent

- **Journal super-agent** (`electron/superagent/`, `docs/SUPERAGENT.md`) : un SQLite local au PC (`userData/superagent.sqlite`). Le process principal écrit. L’écran lit la projection par IPC et n’ouvre pas le fichier. Les fils restent dans `conversations.json`. Un outil appelé avec l’identifiant d’un autre fil le lit. Rien de ce journal (conversations, fichiers, clés, routines) ne part vers Convex, et `convex/evenements.ts` n’est pas le calendrier des travaux. Le watchdog tourne dans l’app, écrit des alertes, n’écrit pas dans le fil surveillé. La routine Tempo reste inactive. L’écran d’un projet laisse la liste des blocages vide. `waiting_machine` est un état du journal : `electron/agents-distants.ts` ne le pose pas. Un commentaire ou une fin de vérification sur une pull request déjà liée au travail rejoint ce travail ; la lecture n’écrit rien au-dehors du journal. Test : `pnpm test:superagent`.
- **Workflows construits par les agents** (`electron/workflows-outils.ts`, module pur généré en `serveur/workflows-outils.mjs`) : `lister_workflows`, `lire_workflow`, `construire_workflow` (étapes par id court, liens, retraits ; l'app place les cartes, `placer` dans `src/lib/workflows/construction.ts`) et `lancer_workflow`, servis par le serveur MCP de l'app et exécutés par l'écran (`src/lib/workflows/outils-agents.ts`, relais `outils:appel` comme les fils). Lire et construire sont libres en accès « projet » (version `agent` gardée avant une modification), lancer suit la règle de l'accès ; une approbation reste à la personne, une étape de workflow ne lance pas de workflow. **En direct** : l'entrée de `construire_workflow` est suivie pendant que le modèle l'écrit (`OUTILS_EN_DIRECT`, `etape-partielle`) et la page Workflows montre le chantier (`src/lib/workflows/chantiers.ts`, hors de l'état enregistré : NEVER dans le reducer, il change à chaque morceau) ; l'aperçu et l'enregistrement passent par le même `construire` (ce qui a été vu est ce qui est gardé), sinon les gestes sont joués un à un (`etatsSuccessifs`). Couleur de l'agent : `--klyra-agent`, classes `klyra-wf-*` de `globals.css`. Sur un VPS : `serveur/workflows.mjs` relaie au PC par le journal (événement `workflow`, route `agent/workflow`, `workflowPourServeur`). **Sur le téléphone** : `workflows.liste` et `workflows.lire` envoient le chantier (`ChantierLu`, `chantierLu` et `listeWorkflows` dans `src/lib/telephone/workflow-etapes.ts` : l'agent, la phase, ses étapes, celle qu'il écrit, ses trois derniers gestes) et le graphe en cours ; un workflow qu'il crée est en tête de la liste avant d'exister ; le téléphone relit chaque seconde pendant les travaux (`RELECTURE_CHANTIER_MS`, `intervalle` d'après la lecture), rien de plus dans le compte (M-7) ; bandeau `BandeauConstructionTelephone`, étapes `klyra-wf-ligne-*`, lecture seule tant que l'agent écrit. Tests : `src/lib/telephone/chantier-telephone.test.tsx`, `pnpm test:workflows`, `xvfb-run -a pnpm test:workflows:app -- --no-sandbox` (après le build ; vrai Claude Code, faux fournisseur, puis un vrai serveur KLYRA local).
- **Routines ≠ workflows.** Une routine = un agent actif, une consigne, un déclencheur, un historique. Le moteur est toujours actif dans le main (`electron/routines/`) ; aucun flag ni ancien minuteur renderer. Le transport `routines-livraison.ts` utilise la file habituelle ; le main réserve durablement le run AVANT l'appel et observe le résultat/les permissions. Le renderer ne décide pas qu'un agent a réussi. NEVER de minuteur de routine dans le renderer ni de code commun avec le moteur des workflows. L'écran Automatisations sépare Routines et Workflows. Agenda/accueil/planning agent lisent le nouveau moteur, jamais l'ancien tableau du workspace (conservé pour sauvegarde). Migration complète sauvegardée avant conversion ; anciennes chaînes bloquées jusqu'au choix explicite. Détail, limites et retour arrière : `docs/ROUTINES.md`. Tests : `pnpm build:electron && pnpm test:routines`.
