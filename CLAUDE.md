# CLAUDE.md — klyra-app

App de bureau interne KLYRA (Electron + Next.js 16). Les règles studio (brand, `klyra-ui`, conventions code) sont dans `../CLAUDE.md` et s’appliquent ici. Ce fichier ne liste que ce qui est propre à ce dépôt.

**ALWAYS lire `docs/JOURNAL.md` en début de session** (décisions, maquettes Figma, ce qui reste à faire) et le mettre à jour en fin de session : c’est l’historique partagé entre les ordis.

## Phase actuelle

Front seul, données factices, **aux couleurs et composants du design system KLYRA** (https://claude.ai/artifact/C3Tqnor89ed3qjk6n1Wben) : l’app doit avoir l’air d’un vrai produit KLYRA, pas d’un wireframe. Les maquettes Figma (section « App KLYRA — wireframes desktop ») donnent la structure des écrans, le design system donne le rendu. On intègre un écran à la fois, dans l’ordre de la checklist du journal.

## Règles propres à ce dépôt

- **Export statique obligatoire** (`output: "export"`, chargé par Electron) : pas de Server Actions, de route handlers dynamiques ni de proxy. Lire `node_modules/next/dist/docs/` avant d’utiliser une API Next (version 16.4, différente des connaissances habituelles).
- **Identifiants en paramètre d’URL** : `/chat?id=…`, `/projet?id=…`. NEVER de route `[id]` : l’export ne connaît que les id présents au build.
- **Données uniquement via les hooks de `src/lib/workspace.tsx`**. Les écrans ne lisent jamais `src/data/mock.ts` directement : c’est ce qui permettra de brancher le back sans toucher aux écrans.
- **Rien n’est rendu au build** (`AppShell` attend l’ouverture de l’app) : les dates des données dépendent du moment de l’ouverture.
- **Tokens** dans `src/app/globals.css`, repris du `tokens.json` du design system. ALWAYS les rôles du design system en classes : `text-texte-principal / -secondaire / -tertiaire / -accent`, `bg-fond-page / -surface / -survol / -surface-grise / -accent`, `border-bordure-subtile / -defaut / -forte / -champ`, `text-icone-defaut / -secondaire / -accent`, `shadow-ombre-xs / -sm / -ambiante / -levee`, `rounded-xs` (6, boutons) à `rounded-3xl`, `ease-sortie`. Les anciens noms (`k1`, `ink`, `fg-1`, `border-1`, `surface-1`…) ne restent que parce que `klyra-ui` les lit.
- **Icônes : uniquement le set officiel** du design system, via `<Icon name="…" />` (`src/components/icons/`). NEVER lucide ni un autre set. Une icône manque : la reprendre du groupe Icons du design system et l’ajouter à `icon-data.tsx` (encre `#303030` → `currentColor`).
- **Boutons : `Bouton` / `BoutonIcone`** (`src/components/ui/Bouton.tsx`, variantes `sombre`, `blanc`, `gris`, `discret`, `ghost`) et `BoutonPrincipal` (noir à écran de points, un seul par écran, sans icône). NEVER le `Button` ni l’`IconButton` de `klyra-ui` : ils sont en pilule et passent au bleu au survol.
- **Autres composants du design system portés ici** : `Onglets`, `PixelCheck` (coche « fait »). De `klyra-ui`, on garde `Input`, `Textarea`, `Avatar`, `Kbd`, `Stack`, `EmptyState`.
- **Listes et fenêtres : jamais de rendu système.** NEVER de `<select>` natif ni du `Select` de `klyra-ui` : `ListeDeroulante` (`src/components/ui/ListeDeroulante.tsx`, variantes `champ`, `puce`, `compact` ; `PuceSelect` dans les composeurs). NEVER `window.alert/confirm/prompt` : `Modale` et `useConfirmation` (`src/components/ui/Modale.tsx`).
- **Réglages** (`src/components/reglages/`) : une section par fichier dans `sections/`, chaque réglage dans une `Ligne` dont l’`id` est aussi déclaré dans `catalogue.ts` (c’est ce que la recherche trouve). Nouveau réglage → l’ajouter aux deux. Ce que le process principal doit connaître (notifications…) passe par `electron/reglages.ts` et `useReglages()` (`src/lib/reglages.ts`). ⌘ , ouvre les Réglages (`useRaccourciReglages`).
- **Consommation** : `electron/consommation.ts` tient un journal (`consommation.jsonl` dans le dossier de l’app) des jetons et coûts renvoyés par Claude Code (écart du `modelUsage` cumulé, à chaque `result`) et par les autres IA (`usage`). Jamais de contenu de message. Le Profil en tire ses chiffres (`src/lib/consommation.ts`) ; NEVER de chiffre estimé ou inventé : sans donnée, un état vide. `electron/historique.ts` rattrape toute la consommation Claude Code du poste dans ses transcriptions (`$CLAUDE_CONFIG_DIR` ou `~/.claude/projects`) : sessions de l’app (marquées `klyra`, seulement avant le journal) et des autres outils ; incrémental. `electron/anthropic-admin.ts` : usage et coût réels d’une organisation Console, facultatif (clé Admin chiffrée). Test : `pnpm build:electron && pnpm test:consommation` (aussi en CI Windows).
- **Computer Use** : l’interrupteur (coupé par défaut) et l’état des autorisations du système, dans les Réglages. Le pilotage suit `docs/COMPUTER-USE-PLAN.md` (validé par Corentin le 29/10), une PR par étape. Couche système dans `electron/ordinateur/` : `coordonnees.ts` (pur, testé), `capture.ts`, `entrees.ts` qui pilote `klyra-entrees` (`native/entrees/`, Swift sur Mac, C# .NET Framework 4 sous Windows, préparé par `pnpm entrees` dans `vendor/entrees/`). ALWAYS `verifierInterrupteur()` (`garde.ts`) avant toute capture ou entrée ; seul `relacherTout()` (arrêt d’urgence) passe outre. Tests : `pnpm test:coordonnees`, `pnpm test:ordinateur` (vrai clic en CI Windows et Mac).
- **Sons** : ALWAYS `jouer("<événement>")` de `src/lib/sons/sons.ts` (un seul AudioContext, réglages, sons de l’interface coupés par le système, dictée, doublons avec la notification), NEVER d’`Audio` ni d’AudioContext ailleurs. Chaque thème est une panoplie complète : les microinteractions (`clic`, `ouvrir`, `fermer`, `selection`) et les événements (envoi, fin de tâche…). Les microinteractions sont branchées sur toute l’app par `src/lib/sons/interactions.ts`, d’après les gestes et l’ARIA : un contrôle sonne seul s’il est un vrai `button` ou lien avec le bon rôle (`tab`, `radio`, `option`, `menuitem`…) ; un menu, popover ou fenêtre a `role="menu"`, `"dialog"` ou `"listbox"`, ou un déclencheur `aria-expanded`. `data-son` précise au besoin (`aucun`, `panneau`, `fermer`…). Nouvel événement → une recette dans chacun des 4 jeux de `themes.ts` (`pnpm test:sons` le vérifie). Un son à côté d’une notification du système : `notificationSonore()` d’abord.
- **NEVER de `.module.css`** : la config Turbopack fait passer tous les `.css` par Tailwind, ce qui casse les CSS modules (le composant s’affiche sans style, sans erreur). Les styles qu’on ne peut pas écrire en classes Tailwind vont dans `globals.css`, en classes préfixées `klyra-…`.
- **ALWAYS `cn` de `@/lib/cn`**, jamais celui de `klyra-ui` : il ne connaît pas nos tailles `text-ui…` et les prend pour des couleurs (texte noir sur bouton sombre). Nouvelle taille ou ombre dans `globals.css` → l’ajouter aussi dans `src/lib/cn.ts`.
- **Logo** : `public/brand/` (générique, signe, icône), copiés du design system. Générique jamais sous 125 px de large.
- **Agents = les vrais fichiers `~/.claude/agents/*.md`**, lus et écrits par l’app de bureau (`electron/agents.ts`, via `window.klyra`, cf. `src/lib/bridge.ts`). NEVER de copie des fiches dans le code : l’écran affiche le fichier, section par section. Préférences personnelles (rôle court, couleur, nom affiché, modèle d’un agent reçu) dans `agents-meta.json` du dossier de l’app. **L’app ne supprime jamais une fiche** : d’autres outils lisent ce dossier.
- **Mes agents** (`electron/mes-agents.ts`, `userData/mes-agents.json`) : les agents choisis par la personne, actifs ou désactivés, leur origine (`local`, `modele`, `bibliotheque` avec le compte qui l’a ajouté, `copie`) et l’empreinte de la fiche écrite par l’app. `useAgents().roles` = l’assistant puis les agents **actifs** seulement (mentions, puces, routines, panneau) ; `tous` = toutes les fiches du poste avec leur statut ; `useRole(id)` connaît aussi les désactivés (anciens messages). Première ouverture de cette version : **reprise** (des données de l’app existent : toutes les fiches présentes actives, assistant « Principal ») ou **nouveau profil** (l’assistant seul, à nommer). `chargerMesAgents` tourne avant la fenêtre.
- **Ce que Claude Code peut appeler** : chaque session lancée par l’app reçoit `--disallowedTools Agent(<nom>)` pour toute fiche lue (dossier de l’utilisateur, `CLAUDE_CONFIG_DIR`, `.claude/agents` du projet et de ses parents) qui n’est pas active, et une règle `ask` sur `Agent` : chaque délégation passe par `agentAutorise` (agents actifs et ceux de Claude Code seulement), même en accès complet. `streamAgent` et `runAgent` refusent un agent inactif (fils, routines, workflows, conversation directe). Rien n’est écrit dans les réglages de Claude Code. Test : `node scripts/test-delegation.mjs` (vrai Claude Code, faux fournisseur local). NEVER filtrer un agent seulement à l’affichage.
- **L’assistant** : id `principal` figé (`dm-principal`, sessions) ; nom et couleur choisis par la personne (`mes-agents.json`), donnés à sa session (`consigneAssistant`). Il répond et fait lui-même ce qui est simple ; avec des agents actifs, il pilote comme un chef de cabinet : brief autonome, un responsable par tâche, pas de travail refait en parallèle, fil existant repris, au plus trois travaux confiés en même temps et deux reprises avant de dire le blocage, preuves vérifiées avant « livré » (règles de conduite, pas un moteur de quotas). Il propose une fiche par l’outil MCP `proposer_agent` : une carte dans le fil, l’éditeur pré-rempli, rien d’écrit avant « Créer l’agent ».
- **Règles injectées à chaque session** (`electron/claude.ts`) : `REGLES_COMMUNES` (l’auteur vérifie lui-même, QA seulement sur demande de la personne pour ce livrable, accès technique ≠ accord, rien d’inventé) vont à l’assistant et à chaque agent, quelle que soit la version de sa fiche ; `consigneAgent` dit aussi qu’on confie par les fils ou un agent actif. Le chemin court `runAgent` (« Modifier avec Lou ») reçoit `CONSIGNE_SEUL` : aucune délégation possible, il livre seul. Ces textes ne contredisent jamais `agents-equipe/` : les changer ensemble.
- **Bibliothèque KLYRA** (`convex/bibliotheque.ts`, `src/lib/bibliotheque.tsx`) : définitions publiées volontairement, membres actifs seulement, auteur seul pour mettre à jour (version attendue) ou retirer. Ce qui part : `preparerPublication` (`convex/model/definitions.ts`, aussi utilisé par le serveur) : en-tête réduit (`CLES_PARTAGEES`), chemins personnels remplacés par `{{chemin:cle}}`, secret = refus. Jamais de cache sur le disque ; chaque lecture dit pour quel membre elle a été faite (`pour`). Une définition ajoutée est gardée à la version choisie (`definitions-recues/`) ; une mise à jour est **proposée**, jamais appliquée seule (`appliquer` refuse une fiche modifiée sauf `forcer`) ; modifier sa consigne dans l’app en fait une copie privée. Ce qu’un agent montre de son lien : `lienDe` (`src/lib/lien-bibliotheque.ts`), seulement pour la session qui l’a ajouté.
- **Avatar d'un agent** : ALWAYS `AgentRond` (par son id, avec pastilles) ou `RoleAvatar` ; hors d'un agent enregistré (aperçu, proposition, grappe) `VisuelAgent` / `RondApercu` avec l'id. Tous posent le visuel de sa fiche (`AgentVisuel` : fond de sa teinte, formes choisies par l'id), le même partout ; le nom ne change pas le dessin. NEVER d'initiale ni de dessin à part pour un agent. Les personnes gardent l'`Avatar` de `klyra-ui` (photo ou initiales). `pnpm test:conversation` vérifie qu'en-tête et fil n'affichent pas d'initiale.
- **Écrire une fiche** : toujours via `useAgents().save` (copie dans l’historique, refus si le fichier a changé depuis l’ouverture). L’`id` d’un agent ne change jamais.
- **Modèles KLYRA** : `agents-equipe/*.md` (texte intégral des 11 fiches) → `pnpm agents:equipe` régénère `src/data/agent-templates.generated.ts`. Une collection facultative de la Bibliothèque KLYRA, ajoutée une fiche à la fois (ou « toute la collection » sur demande), jamais installée d’office. Le bloc « Parler en équipe » est le même dans les 11 (outils réels des fils, agents actifs, réponse de fin) ; pas de roster, de prénom de décideur ni d’outil d’un autre système. **Avant de modifier une fiche**, copier sa version actuelle dans `agents-equipe/versions-precedentes/<nom>.v<N>.md` : c’est ce qui reconnaît une fiche installée et la met à jour sans perte (`src/lib/maj-modele.ts`). Une fiche installée n’est jamais réécrite seule : sa carte porte « Mise à jour », `&mode=maj` compare, reprend ce que la personne n’a pas touché, garde ses modifications, fait choisir les sections modifiées des deux côtés ; en-tête de la fiche (modèle d’IA, prénom, outils) et réglages gardés, ancienne version dans l’historique ; « Plus tard », « Garder ma version » (`ignoree`), « Copier en privé », « Remplacer par le modèle ».
- **Lou** : « Modifier avec Lou » lance Claude Code en local (`electron/claude.ts`, `claude -p --agent prompty`, sans outil d’écriture). Elle propose, l’utilisateur applique.
- **Une seule police : Google Sans Flex.** NEVER d’autre famille, même mono : `--font-mono` pointe sur Google Sans Flex, `.klyra-mono` ne sert qu’à aligner les chiffres.
- **Tailles de texte de l’interface** : tokens `text-ui` (14), `text-ui-s` (13), `text-ui-xs` (12), `text-ui-2xs` (11), `text-ui-3xs` (10). Texte en sentence case, y compris les petits titres de la barre latérale.
- **Mac et Windows** : NEVER « Mac », « Finder » ni « ⌘ » en dur dans un texte de l’interface. Passer par `src/lib/plateforme.ts` (`poste.ce` → « ce Mac » ou « ce PC », `poste.dansExplorateur`, `raccourciDuSysteme("⇧⌘Z")` → « Ctrl+Maj+Z » sous Windows) ; pour les touches, `estMac()` et `avecCommande()` de `src/lib/raccourcis.ts`, qui lisent le même système.
- **Compte d'équipe (Convex)** : seules les données partagées (comptes, équipe, puis rappels et calendrier) vont dans `convex/`, d'après `docs/CONVEX-PLAN.md`. Toute fonction publique commence par `exigerMembre` ou `exigerAdmin` (`convex/model/acces.ts`) et retrouve la personne par sa session, jamais par un argument. Seule exception, avant toute session : `connexion:demanderLien`, qui répond de la même façon pour toute adresse et applique le délai entre deux liens (`convex/model/limites.ts`, horloge du serveur) ; l'app ne demande jamais un lien par `auth:signIn` directement. L'interface passe par `src/lib/compte.tsx` (`useCompte`, `useEquipe`) ; les jetons de session sont chiffrés par `electron/compte.ts`. **Qui est l'utilisateur** : ALWAYS `useWorkspace().moi` (règles de `src/lib/identite.ts` : connecté, nom, rôle et couleur du compte ; sinon le profil de l'ordinateur ; photo et réglages toujours locaux), NEVER `state.currentUser` pour afficher ou nommer quelqu'un ; modifier son nom ou son rôle : `useMonIdentite().enregistrer`. Nouveau code d'erreur → le traduire dans `MESSAGES`. Tests : `pnpm test:convex` (backend en mémoire). Déploiement de dev : `pnpm dev:convex` ; la production n'est déployée que par l'action App.
- **Recherche dans les conversations** (⌘K, bouton du rail) : `FenetreRecherche` (`src/components/recherche/`), montée une fois dans `AppShell` et ouverte par l'événement `klyra:recherche` ; règles pures dans `src/lib/recherche.ts` (en mémoire sur `state.messages`, jamais d'index sur le disque, d'IPC ni de Convex). Ouvrir un message : `/chat?id=…&message=<id>`, que `MessageThread` centre, éclaire (`data-eclaire`) et surligne (`::highlight(klyra-recherche)`, sur les `[data-cherchable]`) avant de retirer le paramètre. Un nouveau texte de message à chercher → le marquer `data-cherchable`.
- **Rappels** (`Tache`, dans `conversations.json`, notifiés par la boucle de `workspace.tsx` quand `!faite && !notifiee && date && heure` est passé) : changer la date ou l'heure remet `notifiee` à faux. Reporter en un clic : `MenuReporter` (`src/components/planning/`), règles pures dans `src/lib/report.ts` (`echeanceReportee`, `reportsProposes`, `reporter`, `reporterParId`, `HEURE_MATIN`) ; il relit le rappel par son id avant d'écrire, car `enregistrerTache` recrée un rappel absent. Une date de rappel affichée porte `data-echeance={id}` (éclairée après un report).
- **Electron** : lancer avec `env -u ELECTRON_RUN_AS_NODE` (déjà dans les scripts). Si cette variable est présente, Electron démarre comme Node et `require("electron")` ne renvoie rien.

## Vérification

`pnpm typecheck && pnpm lint && pnpm build && pnpm test:smoke`, `pnpm test:convex` dès qu'on touche à `convex/`, `pnpm test:identite` et `pnpm test:profil` (après le build ; partie compte avec un backend Convex local jetable, cf. l'en-tête du script) dès qu'on touche au profil ou au compte, `pnpm test:liens` (même backend local) dès qu'on touche à la demande de lien, `pnpm test:conversation` (après le build, profil temporaire) dès qu'on touche à l'en-tête d'une conversation d'équipe, `pnpm test:collage` et `xvfb-run -a pnpm test:coller -- --presse-papiers-jetable` (Linux seulement : il écrit dans le presse-papiers de l'écran virtuel) dès qu'on touche aux pièces jointes ou au collage, `pnpm test:recherche` et `xvfb-run -a pnpm test:chercher` (après le build, profil temporaire) dès qu'on touche à la recherche ou au fil d'une conversation, `pnpm test:report` et `xvfb-run -a pnpm test:reporter` (après le build, profil temporaire, horloge fixée) dès qu'on touche aux rappels ou à leurs dates, et `pnpm test:agents` (après le build, profil et `~/.claude/agents` temporaires) plus `node scripts/test-delegation.mjs` dès qu’on touche aux agents, `pnpm test:modeles` et `xvfb-run -a pnpm test:maj-modeles` (après le build, profil temporaire) dès qu’on touche à `agents-equipe/` ou à la mise à jour des modèles, et `pnpm test:bibliotheque` (même backend Convex local jetable, deux comptes fictifs) dès qu’on touche à la bibliothèque : ils tournent sur des dossiers temporaires, jamais sur les vrais agents. Ne pas vérifier par capture d’écran : Pelin fait la vérification visuelle de son côté ; `test:smoke` lit le texte rendu.
