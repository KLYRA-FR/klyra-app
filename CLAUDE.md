# CLAUDE.md — klyra-app

App de bureau interne KLYRA (Electron + Next.js 16). Les règles studio (brand, `klyra-ui`, conventions code) sont dans `../CLAUDE.md` et s’appliquent ici. Ce fichier ne liste que ce qui est propre à ce dépôt.

**ALWAYS lire `docs/JOURNAL.md` en début de session** (décisions, maquettes Figma, ce qui reste à faire) et le mettre à jour en fin de session : c’est l’historique partagé entre les ordis.

## Phase actuelle

Front seul, données factices, **aux couleurs et composants du design system KLYRA** (https://claude.ai/artifact/C3Tqnor89ed3qjk6n1Wben) : l’app doit avoir l’air d’un vrai produit KLYRA, pas d’un wireframe. Les maquettes Figma (section « App KLYRA — wireframes desktop ») donnent la structure des écrans, le design system donne le rendu. On intègre un écran à la fois, dans l’ordre de la checklist du journal.

## Règles propres à ce dépôt

- **Export statique obligatoire** (`output: "export"`, chargé par Electron) : pas de Server Actions, de route handlers dynamiques ni de proxy. Lire `node_modules/next/dist/docs/` avant d’utiliser une API Next (version 16.4, différente des connaissances habituelles).
- **Identifiants en paramètre d’URL** : `/chat?id=…`, `/projet?id=…`. NEVER de route `[id]` : l’export ne connaît que les id présents au build.
- **Données uniquement via les hooks de `src/lib/workspace.tsx`**. Les écrans ne lisent jamais `src/data/mock.ts` directement : c’est ce qui permettra de brancher le back sans toucher aux écrans.
- **Rien n’est rendu au build** (`AppShell` attend l’ouverture de l’app) : les dates des données dépendent du moment de l’ouverture.
- **Tokens** dans `src/app/globals.css`, repris du `tokens.json` du design system. ALWAYS les rôles du design system en classes : `text-texte-principal / -secondaire / -tertiaire / -accent`, `bg-fond-page / -surface / -survol / -surface-grise / -accent`, `border-bordure-subtile / -defaut / -forte / -champ`, `text-icone-defaut / -secondaire / -accent`, `shadow-ombre-xs / -sm / -ambiante / -levee`, `rounded-xs` (6, boutons) à `rounded-3xl`, `ease-sortie`. Les anciens noms (`k1`, `ink`, `fg-1`, `border-1`, `surface-1`…) ne restent que parce que `klyra-ui` les lit.
- **Icônes : uniquement le set officiel** du design system, via `<Icon name="…" />` (`src/components/icons/`). NEVER lucide ni un autre set. Une icône manque : la reprendre du groupe Icons du design system et l’ajouter à `icon-data.tsx` (encre `#303030` → `currentColor`).
- **Boutons : `Bouton` / `BoutonIcone`** (`src/components/ui/Bouton.tsx`, variantes `sombre`, `blanc`, `gris`, `discret`, `ghost`) et `BoutonPrincipal` (noir à écran de points, un seul par écran, sans icône). NEVER le `Button` ni l’`IconButton` de `klyra-ui` : ils sont en pilule et passent au bleu au survol.
- **Autres composants du design system portés ici** : `Onglets`, `PixelCheck` (coche « fait »). De `klyra-ui`, on garde `Input`, `Textarea`, `Avatar`, `Kbd`, `Stack`, `EmptyState`.
- **Clic droit : ALWAYS `MenuContextuel`** (`src/components/ui/MenuContextuel.tsx`, avec `useMenuContextuel`, `ElementContextuel`, `SousMenuContextuel`, `ActionsRapides`) : posé au pointeur et retourné au bord, clavier complet, focus rendu. Préférences d’un agent dans la barre (`masque`, `muet`, `epingleLe` de `agents-meta.json`, via `useAgents().preferer` ; `rang`, l’ordre choisi en glissant un agent dans son groupe ou par Alt + ↑/↓, via `useAgents().ranger`, règles dans `src/lib/rang-agents.ts`, geste et mouvement dans `useGlisserAgents` : événements du pointeur, pas de glisser natif) : masquer ne le désactive pas, désactiver passe par `useDesactiverAgent`. Test : `xvfb-run -a pnpm test:menu-contextuel` (après le build).
- **Listes et fenêtres : jamais de rendu système.** NEVER de `<select>` natif ni du `Select` de `klyra-ui` : `ListeDeroulante` (`src/components/ui/ListeDeroulante.tsx`, variantes `champ`, `puce`, `compact` ; `PuceSelect` dans les composeurs). NEVER `window.alert/confirm/prompt` : `Modale` et `useConfirmation` (`src/components/ui/Modale.tsx`).
- **Réglages** (`src/components/reglages/`) : une section par fichier dans `sections/`, chaque réglage dans une `Ligne` dont l’`id` est aussi déclaré dans `catalogue.ts` (c’est ce que la recherche trouve). Nouveau réglage → l’ajouter aux deux. Ce que le process principal doit connaître (notifications…) passe par `electron/reglages.ts` et `useReglages()` (`src/lib/reglages.ts`). ⌘ , ouvre les Réglages (`useRaccourciReglages`).
- **Consommation** : `electron/consommation.ts` tient un journal (`consommation.jsonl` dans le dossier de l’app) des jetons et coûts renvoyés par Claude Code (écart du `modelUsage` cumulé, à chaque `result`) et par les autres IA (`usage`). Jamais de contenu de message. Le Profil en tire ses chiffres (`src/lib/consommation.ts`) ; NEVER de chiffre estimé ou inventé : sans donnée, un état vide. `electron/historique.ts` rattrape toute la consommation Claude Code du poste dans ses transcriptions (`$CLAUDE_CONFIG_DIR` ou `~/.claude/projects`) : sessions de l’app (marquées `klyra`, seulement avant le journal) et des autres outils ; incrémental. `electron/anthropic-admin.ts` : usage et coût réels d’une organisation Console, facultatif (clé Admin chiffrée). Test : `pnpm build:electron && pnpm test:consommation` (aussi en CI Windows).
- **Utilisation des abonnements** (anneaux du rail, `UtilisationRail` dans `src/components/chat/CarteUtilisation.tsx`) : un anneau par fournisseur connecté du serveur affiché (`useMoteurs(useLieuActif())`), Claude et ChatGPT par son compte ; lecture par `electron/utilisation.ts` (module pur, généré en `serveur/utilisation.mjs`), méthodes `utilisation` / `surUtilisation` des moteurs, IPC `moteurs:utilisation` aiguillé par le `lieu`, route `moteurs/<id>/utilisation` du VPS. NEVER de chiffre estimé : une fenêtre non donnée reste vide. Relire Claude Code sur ce PC coûte une petite requête (au clic seulement) ; Codex et le VPS se relisent gratuitement. Nouveau moteur à abonnement → son lecteur dans `utilisation.ts` et son logo dans `FOURNISSEURS`. Tests : `pnpm test:moteurs`, `pnpm test:serveur-fournisseurs`.
- **Grok** (moteur `grok`, Grok Build de xAI) : `grok agent stdio`, l'Agent Client Protocol, par un seul client pour le PC et le VPS (`electron/moteurs/acp.ts`, généré en `serveur/acp.mjs` ; PC : `electron/moteurs/grok.ts`, VPS : `serveur/grok.mjs`). Les consignes de la session vont dans `_meta.rules`, l'accès complet dans `_meta.yoloMode`, les autres accès dans `session/set_mode`. Le modèle et l'effort passent par `session/set_config_option` (`{ value }`). Un outil MCP arrive en `serveur__outil` et devient `mcp__serveur__outil`. `ENV_GROK` coupe ce que Grok lirait de Claude Code (skills, MCP) et sa mise à jour automatique. Les skills allumées sont présentées comme pour Codex (`consigneSkillsCodex`). Grok n'appelle pas les agents de l'app (ses sous-agents viennent de `~/.grok/agents`). Connexion : `grok login` sur le PC, `grok login --device-auth` sur le VPS (`lireCodeAppareil`) ; clé de console.x.ai en repli, chiffrée sur le PC (`grok-cle.json`), en 600 sur le VPS (`donnees/grok.json`), donnée au processus seulement (`XAI_API_KEY`). Documentation : celle qui est embarquée dans le binaire (pages `15-agent-mode.md`, `22-permissions-and-safety.md`…). Tests : `pnpm test:moteurs` (faux Grok, `scripts/faux-acp.mjs`), `pnpm test:serveur-grok`, `xvfb-run -a pnpm test:moteur-grok -- --no-sandbox` (après `build:electron`). Avec `KLYRA_GROK_PATH`, les deux derniers tournent sur le vrai Grok Build.
- **Configuration KLYRA** (`electron/configuration-klyra.ts`, module pur lu par le process principal et l'écran ; `reglages.configuration`) : ce que l'app propose pour que les agents consomment moins, adopté en un clic (carte de l'Accueil `CarteConfiguration`, Réglages › Agents `GroupeConfigurationKlyra`), jamais appliqué d'office, modifiable, réversible, et seulement pour les sessions de l'app. **Consignes KLYRA** : un texte ajouté par `consignesApp` (donc Claude Code et Codex), modifiable ; le modèle a une version (`MODELE_CONSIGNES`), un texte resté tel quel suit la nouvelle (`MODELES_PRECEDENTS`), un texte modifié la voit proposée. **Mémoire des agents** coupée : `CLAUDE_CODE_DISABLE_AUTO_MEMORY` dans `environnementAgent` (~4 000 jetons par appel d'un agent qui a `memory`), sans toucher aux fiches. Changer l'un ou l'autre change la signature des sessions (`signatureConfiguration`). Le VPS reçoit la configuration avec l'équipe (`equipePourVps`, dans l'empreinte) et l'applique à toutes ses sessions (PC, téléphone, routines), Codex compris pour les consignes. **Diagnostic du poste** (`electron/diagnostic-poste.ts`, Réglages › Agents) : ce que la configuration personnelle de Claude Code ajoute à chaque appel (CLAUDE.md personnel et ses imports, skills personnelles, présentation des agents actifs, plugins, serveurs MCP), estimé à 2,75 caractères par jeton, avec un conseil et « Montrer » (seulement un chemin que le diagnostic vient de trouver). Les skills personnelles se coupent par agent (Réglages › Agents, `skillsParAgent`) sans retirer les agents ni les CLAUDE.md. `--setting-sources project,local` retire aussi le dossier préparé (agents, skills, CLAUDE.md) : on ne le combine pas avec `CLAUDE_CONFIG_DIR`. `CLAUDE_CODE_DISABLE_CLAUDE_MDS` retire aussi les AGENTS.md des projets. Sur un VPS : Réglages du serveur › Général (« Ce que ce serveur ajoute », route `agent/diagnostic`, module généré `serveur/diagnostic-poste.mjs`), sans « Montrer ». Tests : `pnpm test:configuration` (Electron, vrai Claude Code, faux fournisseur), `src/lib/configuration-klyra.test.ts`, `pnpm test:diagnostic-poste`.
- **Consignes d'un projet** (`electron/consignes-projet.ts`, `ConsignesProjet` sur l'écran d'un projet de ce poste) : « Ajouter les consignes KLYRA » montre d'abord ce qui sera écrit, puis crée un AGENTS.md court à remplir (but, commandes de vérification devinées d'après le package.json et le verrou, où sont les choses, règles) et un CLAUDE.md d'une ligne `@AGENTS.md`. Claude Code le lit alors à toutes les versions, une seule fois (+59 jetons, vérifié), et Codex lit l'AGENTS.md. Jamais d'écrasement : une création échoue si le fichier est apparu (`wx`), un CLAUDE.md existant reçoit seulement l'import en tête, une fois. IPC `projets:consignes` et `…:ecrire`, aiguillés par le `lieu` du projet : sur un VPS, routes `fichiers/consignes` (GET l'état, POST l'écriture) et module généré `serveur/consignes-projet.mjs` ; « Ouvrir AGENTS.md » l'ouvre dans la visionneuse. Tests : `pnpm test:consignes-projet` (module, puis Electron).
- **Taille des conversations** (`src/lib/contexte.ts`, `ConseilContexte`) : chaque appel principal envoie `contexte` (ce qu'il a relu : entrée + cache lu + cache écrit), gardé par agent dans `chat.contexte` avec le socle de la session (premier appel) et la session mesurée ; `/compact` part tel quel (`construirePrompt`), sa réponse est marquée `compaction` (pas une réponse pour `aReprendre`) et `compact_boundary` la termine (résultat vide), en local comme sur le VPS (`serveur/agents.mjs`). Le conseil au-dessus du composeur porte sur les échanges (taille moins socle) : lourde (≥ 50 k) → « Résumer la conversation » ; reprise après plus d'une heure (cache expiré, ≥ 30 k) → « Nouveau fil » là où il y a des fils (un résumé ne rattraperait pas la relecture) ; « Plus tard » jusqu'à +20 k. **Résumé automatique** (configuration KLYRA `resumeAuto`, désactivé par défaut et hors de la configuration recommandée tant qu'il n'est pas mesuré) : l'app envoie elle-même `COMMANDE_RESUME_AUTO` (`/compact` et ce qu'il faut garder) par `compacterAuto` ; la commande reste hors du fil, la réponse porte `compactionAuto` (`envoi` ou `pause`) et une note. Avant un message à un agent dont les échanges dépassent 80 k (`resumeAvantEnvoi`) : le message attend dans la file, le résumé passe d'abord. Pendant une pause de 25 à 55 min avec au moins 40 k d'échanges (`resumePause`) : une tentative par mesure, un à la fois, vérifié 5 s après l'ouverture puis chaque minute. Jamais pendant qu'un agent travaille. Un résumé n'est pas une réponse : ni notification, ni son, ni ticket, ni retour de fil. Pas de `CLAUDE_CODE_AUTO_COMPACT_WINDOW` : Claude Code résume aussi en plein travail, et a un plancher (~75 k). Tests : `pnpm test:contexte`, `pnpm test:conseil-contexte` et `pnpm test:resume-auto` (après le build, profil temporaire).
- **Computer Use** : le pilote est **cua-driver** (trycua, MIT), épinglé dans `cua-driver.lock.json`, préparé par `pnpm cua-driver` dans `vendor/cua-driver/` et embarqué dans l’app, sur le modèle d’OpenBot (`docs/COMPUTER-USE-PLAN.md`, révision du 03/11). `electron/ordinateur/pilote.ts` lance un seul démon (`cua-driver serve`) directement depuis le process principal (macOS donne alors les autorisations à KLYRA), seulement si l’interrupteur des Réglages est allumé ; `relais.ts` est le relais entre les agents et le démon (copie JSON du `structuredContent`). Les agents ont l’entrée MCP « ordinateur » (`serveurOrdinateur()`, dans `configMcp`) seulement quand le pilote est prêt. NEVER re-signer cua-driver sur Mac (il garde la signature Developer ID de son éditeur, `scripts/signer-mac.cjs` le vérifie). Tests : `pnpm test:relais`, `pnpm test:ordinateur` (vrai pilote ; sous Linux, xvfb et un gestionnaire de fenêtres).
- **Navigateur de KLYRA** (`electron/navigateur/`, onglet « Navigateur » des panneaux d’une conversation, `PanneauNavigateur`) : le Computer Use du web, sur le modèle d’OpenBot. Vraies pages (`WebContentsView`) posées par le main sur la zone que l’écran réserve (`usePlacementOnglet`, cadre suivi à chaque image) ; une page native passe au-dessus de tout le HTML : elle s’efface dès qu’un élément de `RECOUVREMENTS` existe (`role` dialog, alertdialog, menu, listbox, ou `data-flottant`) — un nouveau calque flottant au-dessus d’un panneau doit en avoir un. Chaque onglet appartient à une conversation ; l’agent ne voit que les siens (`ongletPourAgent`). Session `persist:klyra-navigateur` à part, seulement http(s), une seule autorisation (presse-papiers en écriture), jamais de preload. Les agents passent par les 5 outils `navigateur_*` du serveur MCP de l’app (`outils.ts`, réglage `navigateur.agents`, dans la signature des sessions) : action par le protocole de débogage, lecture en monde isolé (`regles.ts`), jamais de mot de passe, de code ni de carte (`passer_la_main`). La personne prend la main (`main`), l’agent lit sans agir. Cadres directs lus (`c1e4`), fichiers par `envoyer_fichiers`, clic droit = `MenuContextuel` de l’app (`navigateur:menu`). **Coffre** (`coffre.ts`, `safeStorage`) : NEVER de mot de passe vers l’écran ni vers un agent ; `remplir_connexion` / « Remplir » le posent seulement dans une page de son site. **VPS** : le navigateur reste celui du PC ; un appel d’un agent du serveur passe par le journal (`serveur/navigateur.mjs`, événement `navigateur`) et `executerPourServeur` (conversation de ce lieu seulement) ; outils et consigne dans `definitions.ts`, généré pour le serveur. Tests : `pnpm build:electron && pnpm test:navigateur`, `pnpm test:navigateur-ecran` (après le build ; Linux : `xvfb-run -a … -- --no-sandbox`).
- **Sons** : ALWAYS `jouer("<événement>")` de `src/lib/sons/sons.ts` (un seul AudioContext, réglages, sons de l’interface coupés par le système, dictée, doublons avec la notification), NEVER d’`Audio` ni d’AudioContext ailleurs. Chaque thème est une panoplie complète : les microinteractions (`clic`, `ouvrir`, `fermer`, `selection`) et les événements (envoi, fin de tâche…). Les microinteractions sont branchées sur toute l’app par `src/lib/sons/interactions.ts`, d’après les gestes et l’ARIA : un contrôle sonne seul s’il est un vrai `button` ou lien avec le bon rôle (`tab`, `radio`, `option`, `menuitem`…) ; un menu, popover ou fenêtre a `role="menu"`, `"dialog"` ou `"listbox"`, ou un déclencheur `aria-expanded`. `data-son` précise au besoin (`aucun`, `panneau`, `fermer`…). Nouvel événement → une recette dans chacun des 4 jeux de `themes.ts` (`pnpm test:sons` le vérifie). Un son à côté d’une notification du système : `notificationSonore()` d’abord.
- **Journal super-agent** (`electron/superagent/`, `docs/SUPERAGENT.md`) : un SQLite local au PC (`userData/superagent.sqlite`). Le process principal écrit. L’écran lit la projection par IPC et n’ouvre pas le fichier. Les fils restent dans `conversations.json`. Un outil appelé avec l’identifiant d’un autre fil le lit. Rien de ce journal (conversations, fichiers, clés, routines) ne part vers Convex, et `convex/evenements.ts` n’est pas le calendrier des travaux. Le watchdog tourne dans l’app, écrit des alertes, n’écrit pas dans le fil surveillé. La routine Tempo reste inactive. L’écran d’un projet laisse la liste des blocages vide. `waiting_machine` est un état du journal : `electron/agents-distants.ts` ne le pose pas. Un commentaire ou une fin de vérification sur une pull request déjà liée au travail rejoint ce travail ; la lecture n’écrit rien au-dehors du journal. Test : `pnpm test:superagent`.
- **Coffre** (Réglages › Coffre, sous Agents ; `electron/coffre.ts`, règles pures dans `electron/coffre-regles.ts`, outils dans `electron/coffre-outils.ts`) : clés API, jetons et mots de passe dans `userData/coffre.json`, chaque valeur chiffrée par `safeStorage` ; les connexions de sites restent dans `navigateur/coffre.ts` (même règle) et s'y affichent. NEVER une valeur vers l'écran ni vers un agent : l'écran l'envoie une fois (champ masqué), « Copier » passe par le presse-papiers depuis le main (vidé après 30 s). Un agent a `coffre_lister` (noms), `coffre_demander` (carte `coffre-demande` dans le fil, `CarteCoffre` : la personne y colle la valeur, l'agent ne reçoit que le nom), `coffre_enregistrer` (jamais d'écrasement) et `coffre_ecrire_fichier` (sur accord en accès « Projet » ; refusé dans un fichier que Git suit ou suivrait, les données de l'app, un lien). Jamais de secret collé depuis le téléphone (il passerait par le compte). **VPS** : le coffre reste celui du PC (`configuration.coffre` envoyé avec l'équipe) ; un outil `coffre_*` d'un agent du serveur passe par le journal (`serveur/coffre.mjs`, événement `coffre`, sans valeur : tous les appareils reliés lisent le journal) et `executerCoffrePourServeur` (conversation de ce lieu seulement). La valeur que l'agent range est lue une fois par le PC (`POST agent/coffre`, `lire`) ; pour un fichier du VPS, contrôlé d'abord là-bas (sous le dossier de klyra, hors de `donnees`, hors de Git), le PC rend la valeur au serveur, qui l'écrit. Définitions, textes, règles et écriture de fichier communs (`coffre-definitions.ts`, `coffre-regles.ts`, `coffre-fichier.ts`, générés pour le serveur). Tests : `pnpm test:coffre` (après `build:electron`, dont l'aller-retour avec un vrai serveur KLYRA local), `node --test serveur/coffre.test.mjs` (dans `test:serveur`), `xvfb-run -a pnpm test:coffre-ecran -- --no-sandbox` (après le build ; avec `KLYRA_CLAUDE_PATH`, le vrai Claude Code face au faux fournisseur, sur ce PC puis sur un vrai serveur KLYRA local).
- **Workflows construits par les agents** (`electron/workflows-outils.ts`, module pur généré en `serveur/workflows-outils.mjs`) : `lister_workflows`, `lire_workflow`, `construire_workflow` (étapes par id court, liens, retraits ; l'app place les cartes, `placer` dans `src/lib/workflows/construction.ts`) et `lancer_workflow`, servis par le serveur MCP de l'app et exécutés par l'écran (`src/lib/workflows/outils-agents.ts`, relais `outils:appel` comme les fils). Lire et construire sont libres en accès « projet » (version `agent` gardée avant une modification), lancer suit la règle de l'accès ; une approbation reste à la personne, une étape de workflow ne lance pas de workflow. **En direct** : l'entrée de `construire_workflow` est suivie pendant que le modèle l'écrit (`OUTILS_EN_DIRECT`, `etape-partielle`) et la page Workflows montre le chantier (`src/lib/workflows/chantiers.ts`, hors de l'état enregistré : NEVER dans le reducer, il change à chaque morceau) ; l'aperçu et l'enregistrement passent par le même `construire` (ce qui a été vu est ce qui est gardé), sinon les gestes sont joués un à un (`etatsSuccessifs`). Couleur de l'agent : `--klyra-agent`, classes `klyra-wf-*` de `globals.css`. Sur un VPS : `serveur/workflows.mjs` relaie au PC par le journal (événement `workflow`, route `agent/workflow`, `workflowPourServeur`). Tests : `pnpm test:workflows`, `xvfb-run -a pnpm test:workflows:app -- --no-sandbox` (après le build ; vrai Claude Code, faux fournisseur, puis un vrai serveur KLYRA local).
- **Routines ≠ workflows.** Une routine = un agent actif, une consigne, un déclencheur, un historique. Le moteur est toujours actif dans le main (`electron/routines/`) ; aucun flag ni ancien minuteur renderer. Le transport `routines-livraison.ts` utilise la file habituelle ; le main réserve durablement le run AVANT l'appel et observe le résultat/les permissions. Le renderer ne décide pas qu'un agent a réussi. NEVER de minuteur de routine dans le renderer ni de code commun avec le moteur des workflows. L'écran Automatisations sépare Routines et Workflows. Agenda/accueil/planning agent lisent le nouveau moteur, jamais l'ancien tableau du workspace (conservé pour sauvegarde). Migration complète sauvegardée avant conversion ; anciennes chaînes bloquées jusqu'au choix explicite. Détail, limites et retour arrière : `docs/ROUTINES.md`. Tests : `pnpm build:electron && pnpm test:routines`.
- **NEVER de `.module.css`** : la config Turbopack fait passer tous les `.css` par Tailwind, ce qui casse les CSS modules (le composant s’affiche sans style, sans erreur). Les styles qu’on ne peut pas écrire en classes Tailwind vont dans `globals.css`, en classes préfixées `klyra-…`.
- **ALWAYS `cn` de `@/lib/cn`**, jamais celui de `klyra-ui` : il ne connaît pas nos tailles `text-ui…` et les prend pour des couleurs (texte noir sur bouton sombre). Nouvelle taille ou ombre dans `globals.css` → l’ajouter aussi dans `src/lib/cn.ts`.
- **Logo** : `public/brand/` (générique, signe, icône), copiés du design system. Générique jamais sous 125 px de large.
- **Agents = les fichiers du dossier de l’app** (`userData/equipe/*.md`), lus et écrits par l’app de bureau (`electron/agents.ts`, `electron/mes-agents.ts`, via `window.klyra`, cf. `src/lib/bridge.ts`). NEVER de copie des fiches dans le code : l’écran affiche le fichier, section par section. Le premier lancement copie `~/.claude/agents` dans ce dossier, sans rien y supprimer ni le modifier ensuite. Préférences personnelles (rôle court, couleur, nom affiché, modèle d’un agent reçu) dans `agents-meta.json`. **L’app ne supprime jamais une fiche.** Au lancement d’une session Claude, les fiches actives sont recopiées dans un dossier préparé (`electron/preparation-fournisseur.ts`).
- **Mes agents** (`electron/mes-agents.ts`, `userData/mes-agents.json`) : les agents choisis par la personne, actifs ou désactivés, leur origine (`local`, `modele`, `bibliotheque` avec le compte qui l’a ajouté, `copie`) et l’empreinte de la fiche écrite par l’app. `useAgents().roles` = l’assistant puis les agents **actifs** seulement (mentions, puces, routines, panneau) ; `tous` = toutes les fiches du dossier de l’app avec leur statut ; `useRole(id)` connaît aussi les désactivés (anciens messages). Les outils sont chargés à la demande : seule la consigne de l’assistant pèse sur chaque appel. **Sur un VPS, le même outil** : les règles sont dans `electron/atelier-agent.ts`, `epreuve.ts` et `json-partiel.ts` (modules purs, générés en `serveur/*.mjs`, ajoutés à `lancer.sh`) ; les deux outils sont servis à l’assistant par le serveur MCP du VPS (`serveur/ia.mjs`, `brancherOutils`, en-têtes `X-Klyra-Agent` et `X-Klyra-Conversation`) et répondent par `appelAtelier`, comme `workspace.tsx` sur le PC ; le VPS suit la carte de chaque conversation en mémoire (`suivreAtelier` : une carte créée sur le PC, dont la fiche arrive au VPS, ouvre la suivante), écrit la carte en direct, et fait passer l’épreuve (`POST /klyra/v1/agent/essayer`, IPC `claude:essayer` aiguillé par le `lieu`, `electron/epreuve-vps.ts`) avec son Claude Code ; ce qu’elle consomme est inscrit dans le journal du PC ; la fiche créée s’écrit sur le PC, la source des agents, puis part au VPS. **Sur le téléphone** : le PC plie l’atelier de chaque conversation et copie dans le compte la carte toute calculée (`vueAtelier`, `src/lib/atelier-compte.ts` : une ligne pour un appel plus ancien, la carte entière pour le dernier, fiche et réponses coupées, sans chemin ni secret, version courte si le message dépasse ce que le compte garde) ; ces messages sont recalculés à chaque copie (`SyncCompte`). Le téléphone l’affiche telle quelle (`AtelierTelephone`) et ne fait que demander un geste à l’ordinateur ouvert (`atelier.teinte`, `atelier.essayer`, `atelier.corriger`, `atelier.creer`, `src/lib/telephone/gestes-atelier.ts`) : la carte y est repliée depuis la conversation du PC, jamais d’après le téléphone ; ordinateur fermé, désactivés (P-7). L’épreuve répond tout de suite et ses essais sont notés sur la carte (`essais`, retirés au chargement) : le bureau et le téléphone voient la même épreuve en cours (`jouerEpreuve`, `src/lib/epreuve-atelier.ts`). Les réponses toutes prêtes sont copiées (`choix`) : un clic envoie la réponse comme un message, même ordinateur fermé. « Lui confier » ouvre le formulaire des routines du téléphone, à relire. **Manque, noté** : ordinateur fermé et conversation sur un VPS, la voie directe du téléphone ne montre que le texte (la carte et les choix arrivent à la copie suivante du PC) ; sur un VPS, la carte suivie repart de l’appel suivant après un redémarrage du serveur (la carte affichée vient du fil, sur le PC). Tests : `pnpm test:atelier` (règles, épreuve, JSON partiel, copie pour le téléphone, gestes, fil du téléphone rendu), `xvfb-run -a pnpm test:atelier:app` (après le build, profil temporaire ; avec `KLYRA_CLAUDE_PATH`, le vrai Claude Code face au faux fournisseur : carte en direct, épreuve, correction, création, routine ; puis la même chose sur un vrai serveur KLYRA local, l’app sans Claude Code), `node --test serveur/atelier.test.mjs` (dans `test:serveur`).
